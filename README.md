# Donnar.Tech LINE Backend API

Backend and staff console for the Donnar.Tech LINE Official Account. It handles signed LINE webhooks, deterministic lead qualification, BOT/HUMAN handoff, staff replies and editable bot copy, plus Rich Menu preview and publishing.

The code organization takes inspiration from the modular `endpoint`, `middleware`, and `service` layout in `line-backend-api`; the Donnar-specific flows, data model, and security controls are implemented for this project.

## Local setup

Requirements: Node.js 20 or newer, npm, and a PostgreSQL database (Supabase Free works for a small trial).

```sh
npm install
cp .env.example .env
```

Generate a password hash for the first staff account, then paste it into `STAFF_PASSWORD_HASH` in `.env`:

```sh
node scripts/hash-password.js
```

Set `DATABASE_URL` to a PostgreSQL connection string. Use a Supabase session-pooler URL for hosts with IPv4-only outbound networking, and add `?sslmode=require` if the provider's URL does not already request TLS. Keep real LINE credentials and database passwords outside Git.

For local runs, use a local channel secret and `LINE_FAKE_MODE=true`. It records outgoing messages in memory and makes no LINE API requests.

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

Startup also applies any pending migrations and idempotent bootstrap data before it listens. Open `http://localhost:3000/admin/login`. Webhook endpoint: `POST /webhooks/line`; readiness endpoint: `GET /health/ready`.

## Configuration

| Variable | Purpose |
| --- | --- |
| `NODE_ENV` | Set `production` in deployment. |
| `PORT` | HTTP listen port; defaults to `3000`. |
| `DATABASE_URL` | PostgreSQL connection string; required in production. |
| `LINE_CHANNEL_SECRET` | Required in production to verify webhook signatures. |
| `LINE_CHANNEL_ACCESS_TOKEN` | Required in production for Messaging API replies and Rich Menu publishing. |
| `LINE_FAKE_MODE` | Set `true` locally to use the fake adapter; production always disables it. |
| `STAFF_USERNAME` | Initial staff login name; defaults to `admin`. |
| `STAFF_PASSWORD_HASH` | Scrypt hash generated by `scripts/hash-password.js`; required in production. |
| `PUBLIC_BASE_URL` | Public HTTPS origin used by the deployed console. |
| `LIFF_ID` | Optional LIFF app ID (`1234567890-AbCdEfGh`) for the project intake form. When set, the welcome-card and Rich Menu “ปรึกษาโปรเจกต์” actions open `https://liff.line.me/<LIFF_ID>`. |
| `RICH_MENU_IMAGE_PATH` | Optional override for the 2500 × 1686 PNG or JPEG Rich Menu image (maximum 1 MB). |

Production startup requires `DATABASE_URL`, `LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`, and `STAFF_PASSWORD_HASH`. Inject credentials using the hosting provider's secret manager. The app does not set a webhook URL, disable the OA Manager greeting, or publish a menu on startup.

## Data and behavior

- Customer identity is the LINE user ID; customers do not create accounts.
- PostgreSQL stores conversation state, messages, leads, editable copy revisions, staff sessions, audit events, and Rich Menu publication state.
- Webhook deduplication and event-derived records are written in one transaction. Outbound message outcomes persist as `PENDING`, `SENDING`, `SENT`, `CANCELLED`, or `UNKNOWN`.
- The Thai greeting and deterministic prompts collect service type, project summary, optional budget, and contact preference.
- “คุยกับคน” and the third Rich Menu action switch the conversation to `HUMAN`, send one acknowledgement, and stop bot replies. Staff can inspect the lead, reply, and return the conversation to `BOT`.
- The staff console uses scrypt login, HTTP-only sessions, CSRF checks, editable copy, audit records, and the Donnar.Tech logo.
- Rich Menu creation requires an explicit action in the console and a second confirmation to replace an active menu.
- Rich Menu buttons send visible chat messages that the webhook handles; the artwork is stored as a LINE-ready image in the repository.
- LINE requests use an injectable client. The fake adapter is used for local tests; credentials and customer message bodies are excluded from logs.

## Import existing SQLite data

If an older local SQLite database has data to keep, first make a backup. Apply PostgreSQL migrations to an empty target database, then run the importer explicitly from a trusted local machine:

```sh
DATABASE_URL='postgresql://…' node scripts/import-sqlite-to-postgres.js ./data/donnar.sqlite
```

The import reads SQLite in read-only mode, refuses to write if any target business table has data, preserves IDs and relations, and runs the insert batch in one PostgreSQL transaction. It is never run automatically during deploy. Do not paste the URL or secrets into Git or chat. Verify the imported counts and test staff login before switching traffic.

## Free-tier deployment limits

The Render Blueprint defines one Free web service with no persistent filesystem. PostgreSQL is hosted separately on Supabase; `DATABASE_URL` is injected out of band. Render Free services sleep after inactivity and take time to wake, so the first webhook after idle can be delayed. Supabase Free has a 500 MB database limit and may pause projects after a week of inactivity; it does not include downloadable managed backups. This setup is suitable for testing and a small trial, not a reliability guarantee for a production customer support channel. Export customer data and schedule independent encrypted backups before relying on it.

Keep a single Render instance. Do not store state on its filesystem. Use the Supabase session pooler URL for Render connections, keep SSL enabled, and restrict access to `/admin` at the account/network level as well as using the app login. Configure data retention and deletion before handling real customer conversations.

## Verification

```sh
npm test
npm audit
```

Tests use `pg-mem` and a fake LINE client. They do not call LINE or modify the OA. The SQLite importer uses a small SQLite test fixture.

## LINE OA cutover

The existing OA Manager greeting and manual staff chat remain active. Do not configure the webhook or turn off the greeting until the service is deployed behind HTTPS and a test account has verified follow, text qualification, postbacks, duplicate delivery, invalid signatures, BOT → HUMAN → BOT, staff replies, and Rich Menu behavior. At cutover, configure and verify the webhook in LINE Developers, enable webhook delivery, and disable overlapping OA Manager greeting/auto-reply settings. Keep a rollback path to disable webhook delivery and restore the previous greeting. No live cutover has been performed by this repository.

### LIFF project intake

1. In LINE Developers, open the provider that owns the Messaging API channel and create (or reuse) a **LINE Login channel** there. LIFF apps cannot be added to a Messaging API channel, and a different provider gives a different user ID that will not match the chat.
2. In that LINE Login channel's LIFF tab, add an app with endpoint `https://donnar-line-backend-api.onrender.com/liff/intake`, scope `openid` only, and size Full or Tall. Link the Donnar OA.
3. Set the LINE Login channel to Published (or add testers while it is in Developing).
4. Set `LIFF_ID` in Render and redeploy. The backend derives the expected ID-token audience from the numeric prefix of `LIFF_ID` and verifies tokens with LINE; it never trusts a user ID sent by the page.
5. Republish the Rich Menu from `/admin` only after testing, so its first area opens the form.
