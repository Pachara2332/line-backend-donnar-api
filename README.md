# Donnar.Tech LINE Backend API

Backend and staff console for the Donnar.Tech LINE Official Account. It handles signed LINE webhooks, deterministic lead qualification, BOT/HUMAN handoff, staff replies and editable bot copy, plus Rich Menu preview and publishing.

The code organization takes inspiration from the modular `endpoint`, `middleware`, and `service` layout in `line-backend-api`; the Donnar-specific flows, data model, and security controls are implemented for this project.

## Local setup

Requirements: Node.js 20 or newer, npm, and a PostgreSQL database (Supabase Free works for a small trial).

```sh
npm install
cp .env.example .env
```

Generate a password hash for the first staff account, then paste it into `STAFF_PASSWORD_HASH` in `.env`:

```sh
node scripts/hash-password.js
```

Set `DATABASE_URL` to a PostgreSQL connection string. Use a Supabase session-pooler URL for hosts with IPv4-only outbound networking, and add `?sslmode=require` if the provider's URL does not already request TLS. Keep real LINE credentials and database passwords outside Git.

For local runs, use a local channel secret and `LINE_FAKE_MODE=true`. It records outgoing messages in memory and makes no LINE API requests.

Use a separate local/development database and keep `RESEND_API_KEY` and `RESEND_FROM_EMAIL` blank locally to disable email delivery. `LINE_FAKE_MODE` affects LINE only; configuring both Resend values also enables real email sends during development.

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

Startup also applies any pending migrations and idempotent bootstrap data before it listens. Open `http://localhost:3000/admin/login`. Webhook endpoint: `POST /webhooks/line`; readiness endpoint: `GET /health/ready`.

## Chat Discord notifications

Create a bot application in the Discord Developer Portal, invite its bot to the intended server, and grant it View Channel and Send Messages in the target text channel. Enter `DISCORD_BOT_TOKEN` and `DISCORD_CHANNEL_ID` privately in Render's Environment UI, and set `PUBLIC_BASE_URL` to the deployed HTTPS origin. The Blueprint declares the Discord settings with `sync: false`; never store the token in YAML, logs, Git, or documentation. A server invite link only joins a server and does not create a bot application or provide its token. The bot sends through Discord's REST API; no Gateway connection or privileged intents are needed for these alerts.

If either Discord setting is absent, Discord enqueueing and its worker are disabled. Email retains its own configuration and outbox. Each newly inserted inbound LINE or Messenger `message` event creates one Discord job in the message transaction, in both BOT and HUMAN modes. Duplicate webhook events do not create another job. LINE follow, unfollow, postback, LIFF intake, and Messenger postbacks do not enqueue chat alerts. Messages received while disabled are not backfilled; existing queued jobs wait until configuration is restored.

Alerts contain the cached display name or channel user ID fallback, the platform label and channel user ID, received time, up to 300 characters of text or a message-type label, and a channel-aware `/admin/inbox` link. Sender and preview fields are bounded, customer Markdown is escaped, and allowed mentions are disabled. Media is not downloaded. The CRM link requires staff login. The request content is saved before its first send and reused on retry; the bot token stays only in configuration.

The separate worker claims one job at a time and confirms Discord's returned message ID before marking success. Network failures, HTTP 429 and 5xx retry with exponential delay from 10 seconds up to one hour. HTTP 429 also respects the provider retry delay up to one hour. Other provider rejections and invalid configuration/content become `FAILED`. Claims stuck in `SENDING` for over two minutes become retryable. This sender does not use provider deduplication: an ambiguous timeout or a crash after sending but before saving success can produce a duplicate post. Render Free sleep pauses delivery until the service wakes. Polling stops and the active delivery finishes before database shutdown.

See [Discord activation instructions](docs/deploy-render-line-oa.md#line-chat-discord-notifications) for setup and safe failure inspection.

## Chat email notifications

To enable notifications, verify the sending domain in Resend, then enter `RESEND_API_KEY` and an address on that verified domain as `RESEND_FROM_EMAIL` in Render's environment UI. Set `PUBLIC_BASE_URL` to the deployed HTTPS origin so links open the correct CRM. The Blueprint leaves the key and sender unsynchronized; never put credentials in YAML or Git. If either Resend value is absent, new messages do not create email jobs and the email worker stays disabled; existing chat handling continues. Messages received while disabled are not backfilled on activation.

Each new inbound LINE or Messenger `message` event creates one email job in BOT and HUMAN modes. LINE follow, unfollow, postback, LIFF intake, and Messenger postback events do not create chat emails. Email includes the cached display name (falling back to the channel user ID), channel label and user ID, received time, up to 300 characters of text or a non-text message label, and a channel-aware `/admin/inbox` link. Customer text is escaped in HTML; media is not downloaded. The CRM link requires the normal staff login and does not grant access by itself.

The outbox worker sends independently of the LINE webhook. It retries network failures, rate limits, provider server errors, and concurrent idempotency conflicts with exponential delays starting at 10 seconds and capped at one hour; other provider rejections remain `FAILED`. Jobs left `SENDING` for more than two minutes become retryable. Retries reuse a provider idempotency key, whose retention is 24 hours; an ambiguous send retried after a longer outage can result in a duplicate email. Render Free sleep pauses the worker, so queued email waits until the service wakes and delivery is not guaranteed to be immediate.

For activation steps and safe inspection of failed jobs in a separate local/development database, see [the email deployment instructions](docs/deploy-render-line-oa.md#line-chat-email-notifications).

## Data and behavior

- Customer identity is the LINE user ID; customers do not create accounts.
- PostgreSQL stores conversation state, messages, leads, cached LINE display names/profile photos, editable copy revisions, staff sessions, audit events, and Rich Menu publication state and image drafts.
- Webhook deduplication and event-derived records are written in one transaction. Outbound message outcomes persist as `PENDING`, `SENDING`, `SENT`, `CANCELLED`, or `UNKNOWN`.
- The Thai greeting and deterministic prompts collect service type, project summary, optional budget, and contact preference.
- “คุยกับคน” and the third Rich Menu action switch the conversation to `HUMAN`, send one acknowledgement, and stop bot replies. Staff can inspect the lead, reply, and return the conversation to `BOT`.
- The staff console uses scrypt login, HTTP-only sessions, CSRF checks, editable copy, audit records, and the Donnar.Tech logo.
- The CRM inbox includes unread new-lead alerts and a “รอตอบ” queue. A lead alert is created once with the first lead row; conversations leave the queue only after a later LINE outbound message is recorded as `SENT`.
- LINE display names and profile photos are fetched after webhook processing, cached for up to 24 hours, and shown in the CRM when available. Profile lookup failures do not block replies; unavailable profiles fall back to the LINE UID.
- In `/admin`, staff can upload and preview a Rich Menu draft. Images must be JPEG or PNG, exactly 2500 × 1686 pixels, and at most 1 MB. The validated image is stored in PostgreSQL; invalid uploads leave the current draft and live menu unchanged.
- Upload and preview do not change the LINE OA. Staff must separately confirm `ยืนยันเปลี่ยน Rich Menu` to create the menu, upload the chosen bytes, and set it as default. The previous local publication is retained in history, while its stored image bytes are cleared after a successful switch.
- Rich Menu buttons send visible chat messages that the webhook handles. After publication, users may need to reopen the chat for LINE to display the new default menu.
- B2B quotations: staff create a draft from a CRM conversation, enter buyer company details (tax ID checksum validated) and line items, preview the PDF, then send. Sending freezes the document, snapshots the seller details, assigns a `/q/<token>` customer link, and pushes a LINE card. Numbers run per year as `QT-YYYY-NNNN`; revisions keep the number with an `-R1` suffix and supersede the previous link.
- Quotation totals are calculated on the server in integer satang: VAT 7% (when `SELLER_VAT_REGISTERED=true`) on the discounted amount, optional 3% withholding on the pre-VAT amount, half-up rounding on totals. PDFs are rendered on request with pdfkit and the bundled Sarabun font (SIL Open Font License, `assets/fonts/Sarabun-OFL.txt`).
- Customers can download the PDF and accept (typed name and agreement) or reject once. Expired, superseded and cancelled quotations refuse decisions. Decisions appear in the CRM until staff acknowledge them. The customer link is a bearer link: anyone holding it can view and respond, so share it only with the customer.
- LINE requests use an injectable client. The fake adapter is used for local tests; credentials and customer message bodies are excluded from logs.

## Import existing SQLite data

If an older local SQLite database has data to keep, first make a backup. Apply PostgreSQL migrations to an empty target database, then run the importer explicitly from a trusted local machine:

```sh
DATABASE_URL='postgresql://…' node scripts/import-sqlite-to-postgres.js ./data/donnar.sqlite
```

The import reads SQLite in read-only mode, refuses to write if any target business table has data, preserves IDs and relations, and runs the insert batch in one PostgreSQL transaction. It is never run automatically during deploy. Do not paste the URL or secrets into Git or chat. Verify the imported counts and test staff login before switching traffic.

## Free-tier deployment limits

The Render Blueprint defines one Free web service with no persistent filesystem. PostgreSQL is hosted separately on Supabase; `DATABASE_URL` is injected out of band. Render Free services sleep after inactivity and take time to wake, so the first webhook after idle can be delayed. Supabase Free has a 500 MB database limit and may pause projects after a week of inactivity; it does not include downloadable managed backups. This setup is suitable for testing and a small trial, not a reliability guarantee for a production customer support channel. Export customer data and schedule independent encrypted backups before relying on it.

Keep a single Render instance. Do not store state on its filesystem. Use the Supabase session pooler URL for Render connections, keep SSL enabled, and restrict access to `/admin` at the account/network level as well as using the app login. Configure data retention and deletion before handling real customer conversations.

## Verification

```sh
npm test
npm audit
```

Tests use `pg-mem` and a fake LINE client. They do not call LINE or modify the OA. The SQLite importer uses a small SQLite test fixture.

## LINE OA cutover

The existing OA Manager greeting and manual staff chat remain active. Do not configure the webhook or turn off the greeting until the service is deployed behind HTTPS and a test account has verified follow, text qualification, postbacks, duplicate delivery, invalid signatures, BOT → HUMAN → BOT, staff replies, and Rich Menu behavior. At cutover, configure and verify the webhook in LINE Developers, enable webhook delivery, and disable overlapping OA Manager greeting/auto-reply settings. Keep a rollback path to disable webhook delivery and restore the previous greeting. No live cutover has been performed by this repository.

### LIFF project intake

1. In LINE Developers, open the provider that owns the Messaging API channel and create (or reuse) a **LINE Login channel** there. LIFF apps cannot be added to a Messaging API channel, and a different provider gives a different user ID that will not match the chat.
2. In that LINE Login channel's LIFF tab, add an app with endpoint `https://donnar-line-backend-api.onrender.com/liff/intake`, scope `openid` only, and size Full or Tall. Link the Donnar OA.
3. Set the LINE Login channel to Published (or add testers while it is in Developing).
4. Set `LIFF_ID` in Render and redeploy. The backend derives the expected ID-token audience from the numeric prefix of `LIFF_ID` and verifies tokens with LINE; it never trusts a user ID sent by the page.
5. Republish the Rich Menu from `/admin` only after testing, so its first area opens the form.

Deployment steps are in [docs/deploy-render-line-oa.md](docs/deploy-render-line-oa.md).
