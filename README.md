# Donnar.Tech LINE Backend API

Backend and staff console for the Donnar.Tech LINE Official Account. The repository now contains a local-first implementation for signed webhook intake, deterministic lead qualification, BOT/HUMAN handoff, staff replies and content management, plus Rich Menu preview and publishing.

The code organization takes inspiration from the modular `endpoint`, `middleware`, and `service` layout in `line-backend-api`; this project keeps its own Donnar-specific flows and security controls.

## Local setup

Requirements: Node.js 20 or newer and npm.

```sh
npm install
cp .env.example .env
```

Generate a password hash for the first staff account, then paste the output into `STAFF_PASSWORD_HASH` in `.env`:

```sh
node scripts/hash-password.js
```

Use a local test channel secret and fake LINE adapter for development. `LINE_FAKE_MODE=true` is accepted only outside production; it records outgoing messages in memory and makes no LINE API requests. Do not place real LINE credentials in `.env.example` or commit `.env`.

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

Open `http://localhost:3000/admin/login`. The webhook endpoint is `POST /webhooks/line`; health is `GET /health`.

## Configuration

| Variable | Purpose |
| --- | --- |
| `NODE_ENV` | Set `production` in deployment. |
| `PORT` | HTTP listen port; defaults to `3000`. |
| `DATABASE_PATH` | SQLite file path; defaults to `./data/donnar.sqlite`. |
| `LINE_CHANNEL_SECRET` | Required to verify webhook signatures. |
| `LINE_CHANNEL_ACCESS_TOKEN` | Required for real Messaging API replies and Rich Menu publishing. |
| `LINE_FAKE_MODE` | Set `true` locally to use the fake adapter; production always disables it. |
| `STAFF_USERNAME` | Initial staff login name; defaults to `admin`. |
| `STAFF_PASSWORD_HASH` | Scrypt hash generated by `scripts/hash-password.js`; required in production. |
| `PUBLIC_BASE_URL` | Public HTTPS origin used by the deployed console. |
| `RICH_MENU_IMAGE_PATH` | Optional override for the 1200 × 405 PNG seed image. |

Production startup requires `LINE_CHANNEL_SECRET`, `LINE_CHANNEL_ACCESS_TOKEN`, and `STAFF_PASSWORD_HASH`. Inject them with the hosting provider's secret manager. The app does not set a webhook URL, disable the OA Manager greeting, or publish a menu on startup.

## What is implemented

- Webhook raw-body signature verification using HMAC-SHA256 and constant-time comparison. Invalid signatures are rejected before JSON parsing or event processing.
- Idempotent event storage, conversation/message/lead persistence, serialized outbound sends with PENDING/SENDING/SENT/CANCELLED/UNKNOWN delivery states, and event redelivery handling. Definite rate limits can retry; ambiguous network outcomes remain visible as UNKNOWN for staff review rather than risking duplicate messages.
- Thai greeting and deterministic intake prompts for service type, project summary, optional budget, and contact preference.
- “คุยกับคน” and the third Rich Menu action switch the conversation to `HUMAN`, send a single handoff acknowledgement, and stop bot replies. Staff can inspect the lead summary, reply, and explicitly return the conversation to `BOT`.
- Authenticated staff console with secure HTTP-only sessions, CSRF checks on changes, editable message drafts, publishing audit trail, and the supplied Donnar.Tech logo.
- Rich Menu preview and an explicit create/upload/publish action. A second active menu requires confirmation bound to the exact current publication; interrupted creates are recovered into a reviewable failed state on restart. Publishing uses the three actions: qualify, services, and human handoff.
- LINE API calls are behind an injectable client, with a fake adapter for local tests. Credentials and customer message bodies are excluded from application logs.

## Data and deployment limits

This first implementation uses SQLite so the whole backend can be exercised locally without Docker or a separate database. Deploy it as a **single instance with a persistent, private writable volume** for `DATABASE_PATH`; back up that file using the host's supported backup mechanism. The volume should be encrypted at rest because conversations contain customer information. SQLite is not configured for horizontal scaling. Move the persistence layer to PostgreSQL before using multiple application instances or if the hosting service cannot guarantee durable storage.

Terminate HTTPS at a trusted reverse proxy or hosting platform and use `NODE_ENV=production` so session cookies are marked `Secure`. Restrict access to `/admin` at the account level as well as using the application login. Configure retention and deletion rules for customer conversation data before production use.

## Verification

```sh
npm test
npm audit --omit=dev
```

Tests use an in-memory SQLite database, test-only signing secrets, and a fake LINE client. They do not call LINE or modify the OA.

## LINE OA cutover

The existing OA Manager greeting and manual staff chat remain active. Do not configure the webhook or turn off the greeting until the service is deployed behind HTTPS and a test account has verified follow, text qualification, postback actions, duplicate delivery, invalid signatures, BOT → HUMAN → BOT, staff replies, and the Rich Menu flow. At cutover, configure the webhook URL, enable webhook delivery, and disable overlapping OA Manager greeting/auto-reply settings. Keep a rollback path that disables webhook delivery and restores the prior OA greeting. No live cutover has been performed by this implementation.
